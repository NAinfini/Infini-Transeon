# 3. 三套结构性重设计方案

三案在导航模型、页面层级、仪表盘定位、配置组织方式上互斥,不是同一布局换皮。

---

## 方案 A — "启动台双时态"(任务优先,双模式应用)

### 核心哲学
UI 显式建模两个时态:默认打开的是一个**紧凑启动台**(小窗,类似游戏启动器),深度配置在按需展开的**工作室模式**(全窗)。配置与运行彻底分离。

### 导航模型
无常驻侧栏。启动台只有档案列表 + 启动按钮 + 状态条;右上"工作室"按钮切换到全窗模式,工作室内用顶部横向分区(档案/服务/设置/活动)。

### 页面图
```text
启动台(默认, ~480×640 紧凑窗)          工作室(全窗)
┌────────────────────────┐    ┌─────────────────────────────────┐
│ ● 引擎:翻译中  [工作室]│    │ 档案 | 服务 | 活动 | 设置        │
│ ┌────────────────────┐ │    ├─────────────────────────────────┤
│ │▶ 原神  运行中  ⏸ ■ │ │    │ (各分区内容,档案分区含         │
│ │▶ 女神异闻录  就绪   │ │    │  工作台画布)                    │
│ │▶ 塞尔达  凭据缺失   │ │    │                                 │
│ └────────────────────┘ │    │                                 │
│ [＋新建]      [托盘化] │    └─────────────────────────────────┘
└────────────────────────┘
```

### 主工作流示例
日常启动:开启动台 → 点档案行的 ▶ → 窗口自动托盘化。两步,零切页。

### 强弱与适用
- **强:** 与产品双时态完全同构;日常启动路径最短;紧凑窗天然适合常驻屏角。
- **弱:** 两个窗口模式 = 两套布局系统,WinUI 单窗口内做模式切换的窗口尺寸管理复杂;工作室内部仍需完整二级导航,复杂度只是被推迟;"启动台"对首次用户无引导性。
- **适用:** 档案已稳定、以日常使用为主的成熟用户群。
- **实施复杂度:** 高(窗口模式管理 + 两套外壳)。
- **风险:** WinUI 3 的 AppWindow 尺寸切换与 Mica/标题栏定制交互多坑;紧凑窗内错误呈现空间不足。

## 方案 B — "档案即工作区"(实体优先,主从结构)

### 核心哲学
档案是唯一的一等实体。选中档案即进入其**工作区**,一个档案的所有配置(捕获/区域/通道/覆盖/语言语境/历史)作为工作区内部分节,不再散落各页。全局事务(提供商、应用设置、活动)降级为侧栏底部维护区。

### 导航模型
左侧栏两段式:上段 = Home(启动台页)+ 档案工作区入口;下段(页脚)= 活动、提供商、设置。进入档案工作区后,侧栏切换为**工作区分节导航**(带返回 Home 的面包屑),形成两层导航而非平铺。

### 页面图
```text
Home(默认)                         档案工作区(选中某档案后)
┌──────┬──────────────────┐   ┌──────┬──────────────────────┐
│ 🏠Home│ 运行中: 原神 ⏸■  │   │ ←原神 │ [概览]               │
│──────│ ┌────┐ ┌────┐    │   │ 概览  │  就绪清单/启动/摘要  │
│      │ │原神│ │P5R │ ＋ │   │ 捕获与区域(画布)           │
│      │ └────┘ └────┘    │   │ 翻译通道                    │
│──────│ 最近活动/错误     │   │ 覆盖样式(实时预览)         │
│ 活动 │                  │   │ 语言与语境(术语+提示词)     │
│ 提供商│                  │   │ 历史                        │
│ 设置 │                  │   └──────┴──────────────────────┘
└──────┴──────────────────┘
```

### 主工作流示例
调整某游戏的覆盖样式:Home → 点档案卡(非启动区)→ 工作区侧栏"覆盖样式" → 改参数,实时预览,粘性保存栏。全程无模态。

### 强弱与适用
- **强:** 与用户心智模型("我的这个游戏的设置")完全一致;工作台 33 控件检查器被拆成 4 个专注分节;术语表/历史找到自然归属;导航孤儿问题根治;向导可以复用工作区分节做"引导模式"。
- **弱:** 两层导航需要清晰的进出转场(面包屑/返回),做差了会迷路;跨档案对比(如两个档案的历史)需要额外全局视图;Home 与工作区"概览"有信息重叠风险。
- **适用:** 配置深度大、单档案内容多的产品——正是本产品。
- **实施复杂度:** 中(单一外壳,NavigationView 换 MenuItemsSource 即可实现两态侧栏)。
- **风险:** 工作区分节间共享未保存状态(区域改了没保存就切到通道节)需要统一的工作区级脏状态模型。

## 方案 C — "任务控制台 + 命令面板"(运行时优先,单仪表盘)

### 核心哲学
一个常驻仪表盘 = 实时运行状态墙(目标卡片、实时译文流、延迟/费用),一切配置通过**抽屉**(右滑面板)在仪表盘上就地打开,Ctrl+K 命令面板作为主导航。键盘优先、高密度。

### 导航模型
无传统侧栏。顶栏:状态 + 搜索/命令面板;仪表盘网格 = 运行目标 + 档案;任何实体点开是右侧 40% 宽抽屉(可叠一层);全局设置也是抽屉。

### 页面图
```text
┌─────────────────────────────────────────────┐
│ ● 翻译中   [Ctrl+K 命令/搜索]        ⚙ 🔔  │
├──────────────────────────┬──────────────────┤
│ 运行墙                    │ (点开实体时)     │
│ ┌────────┐ ┌────────┐   │ ┌──────────────┐ │
│ │原神     │ │P5R     │   │ │ 抽屉:区域    │ │
│ │实时译文流│ │ 就绪 ▶ │   │ │ 检查器/画布  │ │
│ │p95 180ms│ └────────┘   │ │              │ │
│ └────────┘               │ └──────────────┘ │
└──────────────────────────┴──────────────────┘
```

### 主工作流示例
改某区域优先级:Ctrl+K → 输"原神 对话框区域" → 抽屉直达该区域检查器。专家路径极短。

### 强弱与适用
- **强:** 实时性最强(译文流是一等公民);专家效率最高;单页面架构状态管理集中。
- **弱:** 抽屉宽度撑不下区域画布这种大工作面(仍要全屏态,等于变相多页);命令面板对首次用户零引导;与 WinUI 控件习惯差异大,自绘成本高;产品明确"游戏期间不看应用窗口",实时墙的核心价值场景其实很窄(游戏时窗口是关着的)。
- **适用:** 需要长时间盯着监控面板的运维型用户——不是本产品主场景。
- **实施复杂度:** 高(命令面板、抽屉系统、虚拟化译文流全部自建)。
- **风险:** 把投资押在"游戏时看不到的界面"上;可访问性(抽屉焦点困住、命令面板读屏)工作量大。

## 3.4 对比总表

| 维度 | A 启动台双时态 | B 档案工作区 | C 任务控制台 |
|---|---|---|---|
| 与产品双时态契合 | ★★★ | ★★☆ | ★☆☆ |
| 与用户心智模型契合 | ★★☆ | ★★★ | ★★☆ |
| 根治 33 控件检查器 | ★☆☆(推迟) | ★★★(拆节) | ★★☆(抽屉仍挤) |
| 根治导航孤儿 | ★★☆ | ★★★ | ★★★ |
| 日常启动步数 | ★★★ | ★★☆ | ★★☆ |
| 首次用户引导性 | ★☆☆ | ★★★ | ★☆☆ |
| WinUI 实现风险 | 高 | 低 | 高 |
| 可访问性成本 | 中 | 低 | 高 |

结论见第 4 章:**以 B 为骨架,吸收 A 的托盘/紧凑启动要素与 C 的实时活动流(降级为 Home 面板)。**
